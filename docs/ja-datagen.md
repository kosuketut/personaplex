# 日本語 PersonaPlex の本データ生成パイプライン

作成日: 2026-10-02 / 対象: `japersonaplex/datagen/`、`scripts/datagen.sh`。設計は `docs/ja-data-spec.md`（以下 §n はその節）。

仮データ（`synth_pilot.py`: テンプレート台本 + pyopenjtalk、単語時刻はモーラ数の按分）を、部品選定（`data/bakeoff/README.md`）で選んだ部品に置き換えた。

| 段 | モジュール | 部品 | 環境 |
|---|---|---|---|
| 台本 | `scripts_llm.py` | Qwen/Qwen3-30B-A3B-Instruct-2507-FP8（vLLM）。固有名詞は IPAdic の読み付き辞書（`names.py`） | `data/envs/llm` |
| 発話の音声 | `tts.py` | Qwen/Qwen3-TTS-12Hz-1.7B-Base。声は YODAS2 由来の 48 話者（`data/voicebank/refs_v0`） | `data/envs/tts` |
| 単語時刻と品質検査 | `align.py` | CTC 2 種 + Qwen3-ForcedAligner のアンサンブル。検査は CTC、whisper medium、ひらがな CTC | `data/envs/align` |
| 対話の組み立て | `assemble.py` | §3 の間合い、相槌、割り込み、音量 | `.venv` |
| トークン化 | `japersonaplex/prepare.py` | 既存のまま | `.venv` |

## 使い方

```bash
# 台本（数分。GPU 1 枚を専有できると約 1,400 トークン/秒）
PYTHONPATH=. CUDA_VISIBLE_DEVICES=1 data/envs/llm/bin/python -m japersonaplex.datagen.scripts_llm \
    --n 192 --scenario mix --seed 1 --out data/datagen/m2/scripts.jsonl --only-passing
# 音声から npz まで（品質検査に落ちた発話は最大 3 回まで作り直す）
scripts/datagen.sh data/datagen/m2/run1 data/datagen/m2/scripts.jsonl 1
```

評価セット（§6.1）: `scripts_llm.py --split heldout` で評価専用の名前（H-name）、`--domains heldout` で評価専用の業種（H-domain）、`tts.py --voice-split heldout` で評価専用の声（H-voice）。軸は混ぜない。

環境の作り方は各モジュールの docstring にある。辞書は `data/dict/ipadic`（`names.py` の docstring の手順で取得）。

## 一貫性の要点

- **単語の単位を 1 つにする**（`units.py`）: 台本の発話を pyopenjtalk で単語に分け、固有名詞は 1 単位にまとめて辞書の読みで上書きする。この同じ単位列から、TTS の入力（名前は読みのかな）、アライナの入力（表記と読み）、テキストストリーム（表記。句読点は前の単語に付ける）を作る。
- **数字はテキストストリームでは算用数字**（v2、2026-10-02）: pyopenjtalk は算用数字を漢数字に正規化するので、元の文と 1 文字ずつ対応させ、数字の範囲にかかる単位を 1 単位にまとめて表記を台本の算用数字（「1050」）に戻す。漢数字は `spoken` に残し、TTS の入力とアライナにはこれを使う（どちらも v1 と同じ文字列になることを pilot40 の 2,429 発話で確認）。理由: 元のモデル（llm-jp-moshi）はテキストストリームに算用数字を出し、プロンプトも算用数字なので、漢数字だと言い換えが要る（v1 は pilot の flip の値段の質問が 0/8）。`NPZ_KANJI=1` で、同じ音声から数字を漢数字にした npz（`npz_kanji`）も作れる（A/B 用）。
- **名前は TTS に読みのかなで渡す**: 漢字のまま渡すと意図した読みになるのは 5/16、かなにすると 15/16（`data/bakeoff/README.md`）。
- **名前の読みが複数ある表記は使わない**（§1.7-5 の案 A）。辞書に 1 つしか読みが載っていない表記は通る（例: IPAdic の「東海林」は「しょうじ」だけ）。
- **語彙に無い文字を含む名前は使わない**: 辞書の名前の約 1.5%（龝山、中嶌など）は llm-jp の SPM で未知語になり、プロンプトでもテキストストリームでも名前が欠ける。
- **割り込み**: agent の発話の 50〜90% の位置の単語境界で user が話し始め、agent はその 0.3〜0.8 秒後に止まる。止めた後に始まる agent の単語はテキストからも消す（§3.5）。
- **作り直しでは漢字もかなで渡す**: Qwen3-TTS は珍しい漢字を読み違え、作り直しても同じ誤りを繰り返した（承って → 「ほまって」、男体山、丑の日）。1 回目は漢字かな交じりで渡し、2 回目以降は漢字を含む単語を pyopenjtalk の読みのかなにする（`units.tts_text(kana_for_kanji=True)`）。

## ターンテイキング（`assemble.py`、`turntaking.py`）

- 話者交替の間隔（§3.2 の分布）は、前の話者の最後の単語の終わりから測る（wav の末尾の無音からではない）。
- 発話の内側の 0.6 秒を超える無音は 0.15〜0.6 秒に詰める（§3.4）。
- 聞き手の相槌を、話し手の 3 秒以上の発話の切れ目（句読点の後か、150 ms 以上の間）に差し込む（§3.3）。相槌の音声は声と役割ごとに先に作り（`tts.py --backchannels`、1 語 3 通り）、長さ 0.15〜0.8 秒と読み（ひらがな CTC）で選別して使い回す。agent の相槌はテキストストリームにも入れる。
- 台本の相槌（type が backchannel）のうち 12 字以下・0.8 秒以下のものは、前の話し手の発話の切れ目に重ねる。それより長いものは普通のターンとして置く。

## 品質検査（`align.py` と `assemble.py`）

発話ごとに次のどれかに当たれば作り直す（`MAX_ATTEMPTS`、既定 3 回。M2 は 5 回）。それでも落ちる発話を含む対話は捨てる。

| 検査 | 閾値 | 理由 |
|---|---|---|
| CTC が聞いた、台本の文字が割り当たらない音声（unexplained_speech_s） | 0.3 秒超 | TTS の付け足し・繰り返し |
| whisper medium の CER（フィラーと「はい」と固有名詞の部分を除く） | agent 0.10、user 0.30 超 | 内容の誤り。whisper はフィラーや文頭の「はい」を書かず、珍しい名前を別の漢字で書く。user は仕様（§6.3）の 0.15 から緩めた（user の音声は学習の正解ではなく、whisper が口語を書き換える誤検出が多かった） |
| 固有名詞の読み（ひらがな CTC の書き起こしに、読みに近い部分文字列があるか。濁点の有無は区別しない） | 編集距離が読みの長さの 1/3 超（最低 1） | §6.3 の名前の照合。ひらがな CTC は清音と濁音をよく取り違える |
| 話速（6 モーラ以上の発話） | 3〜9 モーラ/秒の外 | §5.3。速すぎる発話はフィラーの読み飛ばしを含むことがあった |
| 台本の相槌の長さ | 0.15 秒未満 | 0.8 秒を超えるものは普通のターンとして置く |

対話ごとに、テキストトークンのあふれ（§5.3: 前の単語とぶつかって 3 フレーム超ずれた単語が 2% 超）でも捨てる。

## 結果

### M1（bakeoff の LLM 台本 12 本、2026-10-01）

- 12 対話 → 品質検査と作り直し → 10 対話（0.16 時間）。捨てた 2 対話は、「城下」を読み違えた発話と、台本に英字（「Ｉｅａｔａｐｐｌｅｓ」）が入った発話を含むもの。
- 品質検査の誤検出を 2 つ直した: whisper がフィラーを書き起こさないこと、珍しい名前を別の漢字で書くこと（例: 谷口レンタカー店 → 谷口蓮太カーテン）。
- テキストトークンのあふれは 0。npz は `data.py` で読め、`train.py` の 6 ステップで検証損失が 3.99 → 2.63 に下がった（学習と検証が同じ 10 対話なので、動作確認の意味しかない）。

### M2（辞書の名前を使った LLM 台本、2026-10-02）

- 台本: Qwen3-30B-A3B-Instruct-2507-FP8 で 288 本（seed 0 の 96 本と seed 1 の 192 本）。GPU を専有すると 1,380 トークン/秒、1 本あたり約 670 トークン。自動検査の合格は seed 1 で 67%（相槌の付け間違いを付け替えるようにした後。落ちた理由の最多は、プロンプトに無い数字を agent が言うこと）。合格した 165 本を使った。
- 名前の異なり数: 165 対話で 244 表記（担当者・客・店名）。
- 音声: 1,976 発話（2.6 時間）を 1,034 秒で合成（共有中の GPU で、実時間の約 9 倍の速さ。バッチ 64、`--token-budget 6000`）。品質検査と作り直し（2 回目以降は漢字をかなにする）を 5 回まで行い、149 対話（2.38 時間、平均 57.5 秒）が残った。捨てた 16 対話の理由は whisper の CER 12 件、相槌の長さ 7 件、話速 1 件（相槌の長さはその後、普通のターンとして置くように変えた）。
- 内訳: 雑談 59、サービス 50、QA 40。割り込み 49 回、相槌は台本由来 42 回と差し込み 680 回。
- npz 149 本（`data/datagen/m2/run1/npz`）。`train.py` を 4 ステップ回し、別の 6 対話（`scripts/datagen.sh` の通し確認で作ったもの）での検証損失が 4.30 → 3.69 に下がった（動作確認の意味しかない）。差し込んだ agent の相槌（「はい」など）がテキストストリームに入ることも確かめた。

### データ v3（Seiran、RUN=pilot40v3、2026-10-04）

v2 で学習したモデルは、学習台本に少ない項目の事実を聞かれると答えない（`docs/ja-pilot40-train.md` の「データ v3 に向けた確認」）。
台本で facts の項目を指定して種類を平らにし、そのうち 2 項目を user に項目名で直接聞かせる（`scripts_llm.py --fact-items sample --ask-facts 2 --ask-first 0.5`）。
数字の表記と、台本以外の工程は v2（算用数字）と同じ。QA と評価用の台本は作らない（評価は pilot40 の flip40 v2 を使い続ける）。

```bash
RUN=pilot40v3 SEED=3000 KINDS="main" MAIN_SHARDS=32 N_SERVICE=7000 N_CASUAL=1700 N_QA=0 N_EVAL=0 \
  SERVICE_ARGS="--fact-items sample --ask-facts 2 --ask-first 0.5" bash slurm/submit_datagen.sh
```

本数は v2 の約 2 倍（main 約 70 h）。シャードは interleave で分けるので、シャード 0〜15 だけで約 35 h の部分集合になる（v2 との比較用）。

| 指標（サービスの台本） | v2（学習分） | v3（合格した台本） |
|---|---|---|
| 台本の合格率（サービス / 雑談） | 66% / 75% | 56% / 72% |
| 台本数（サービス / 雑談） | 1,816 / 573（組み立て後） | 3,923 / 1,231（組み立て前） |
| 最初の user 発話で数字の事実を聞き、次の agent 発話で答える | 9% | 59% |
| 数字の事実のうち、聞かれた直後に答えるもの | 43% | 76% |
| 数字の事実のうち、対話で一度も言わないもの | 32% | 19% |
| 数字の事実の項目の種類 | 411 | 1,067 |
| 数字の事実のうち営業時間・受付時間 | 18% | 7% |

- 「聞く」は user の発話に項目名の先頭 2 文字が出ること（粗い数え方）。最初の発話で聞く台本は指示した 47% より多い 59%。
- サービスの不合格の最多は、指定していない営業時間の類を LLM が足したもの（1,346 本）。v3 の検査だけで落ちたのは 627 本。
- 台本 9290 は 26 分（サービス 7,000 本の生成 17 分）。

### データ v4（Seiran、RUN=pilot40v4、2026-10-04）

v3 で学習したモデルは、項目名で聞かれれば答えるが、事情を添えた質問や間接の質問（「〇曜日ってやってますかね」）では v2 と同じだった
（`docs/ja-pilot40-train.md` の「質問の形を変えた評価セット」）。v3 から 2 点だけ変える。

- user の聞き方を 4 つの形に混ぜる（`--ask-forms name:0.2,paraphrase:0.25,situational:0.3,indirect:0.25`）。
  項目名で直接・項目名を使わない言い換え・同じ発話で事情を言ってから聞く・値を直接聞かず「大丈夫ですか」と聞く（agent は値を言って答える）。
- 営業時間の類を入れる台本を 30% → 55%（`--p-hours 0.55`）。数字の事実のうち営業時間の類は、試し生成で 12〜14%（v2 18%、v3 7%）。

検査を足した: 項目名で聞く形以外では、聞く発話に項目名が無いこと。事情を添えた形は聞く発話が 25 字以上。agent の答えに、直前の user の発話に無い値の数字が出ること
（試し生成で、agent が言う前に user が値を知っている台本「3名様で1280円って、一人分ですかね」があった。v3 の合格台本でも 2.5%）。

## 未決のこと

- **QA の事実**: 台本 LLM が作る QA の事実に誤りが混じる（例:「カエルは卵からヒキガエル、その後アメンボになる」）。
  pilot40 の QA を無作為に 12 本読むと 4 本にはっきりした誤り（七五三の年齢、台風の定義、実在しない用語「冷気雨」、
  ペットボトルの「瓶を外す」）。プロンプトに無いことを agent が付け足して誤る例もある。初回学習は QA を除き main だけにした（2026-10-02 決定）。人が確認した知識の一覧から事実を渡す方式に変えるか判断が要る。また §2.2 の先生役の基準形 T0 は情報欄の無い固定文だが、生成器の QA の書式は情報欄付きで、仕様と違う。
- **声バンクの評価専用の声**: 7 声のうち 6 声が女声（F0 による推定）。
- **省いた仕様**: user の発話内のポーズの挿入（§3.4）、声のピッチ・フォルマント加工（§4.3）、user 側の雑音データと残響（§4.2。今は −65 dBFS 前後の白色雑音とゲインのばらつきだけ）、声プロンプトの品質ゲート（§4.4）、台本の MinHash による重複除去（§6.3）。
- **台本の重複**: seed を変えて生成しているだけで、内容の重複は調べていない。
